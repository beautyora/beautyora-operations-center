# 신규 브랜드 Drive 폴더 전환

이 문서의 등록기 미확인 내용은 PR32 당시 조사 결과입니다. 이후 확인된 실제 등록 경로 삭제와 복구/활성화 절차는 [입점 등록 복구](BRAND_INTAKE_RECOVERY.md)를 참고하세요.

## 확인 범위

운영센터 main `89c10679fb2461d4556cb1ddc464fd894c1ebe8c`(PR31), 브랜드 랜딩 main `a0c5c82`를 확인했다. 랜딩 `google-apps-script/form-bridge.gs`는 `FormResponse.submit()` 후 반환한다. 중복 확인 → Notion 등록 → BO ID 발급을 담당하는 별도 프로젝트 소스/ID는 두 저장소에 없다. FormResponse.submit()이 form-submit 트리거를 실행한다고 가정하지 않는다.

이 변경의 범위는 **신규 Notion 페이지 + 확정 BO ID → Drive**다. 등록 함수 내 동기 실행이 아니라 기존 1분 트리거 감지이며, Apps Script 지연/오류 시 더 늦어질 수 있다. 랜딩 → Notion E2E는 별도 등록 프로젝트 확인이 필요하다. 랜딩 저장소는 변경하지 않는다.

## 보호 장치

초기 설정은 기존 Notion 페이지 ID 전체를 읽어 제외 스냅샷으로 저장한다. `BO_BRAND_FOLDERS_EXCLUDED_0`부터 100개씩 나누고, 모든 조각 저장 후 `BO_BRAND_FOLDERS_BASELINE` manifest를 마지막에 기록해 활성화한다. `BO_BRAND_FOLDERS_START_AT`은 활성화 시각 표시용이며 단독으로는 처리를 활성화하지 않는다. 재실행은 이미 확정한 스냅샷을 유지한다.

[Notion 생성시각은 분 단위로 내림된다](https://developers.notion.com/guides/resources/historical-changelog#last-edited-and-created-time-properties-are-now-rounded-to-the-nearest-minute). 따라서 조회 시작은 **스냅샷 읽기 시작시각을 분 단위로 내린 시각**이며, 겹치는 분의 기존 페이지도 ID 스냅샷으로 제외한다. 예: 설정13:52:30, 신규등록13:52:40의 created_time13:52:00도 처리하되 같은 분의 기존 브랜드는 제외한다. 스냅샷 조회 후 저장 중에 등록되어 스냅샷에 없는 페이지도 감지한다.

전환 기준은 성공적으로 저장한 초기 스냅샷이다. 조회 도중 결과에 포함된 페이지는 활성화 전 기존 페이지로 분류된다. 성공한 활성화 이후 새 페이지는 스냅샷에 없으므로 같은 분에도 누락되지 않는다. 전환 작업 중 조회 결과에 포함된 실제 신규 브랜드가 있으면 개별 처리한다. 외부 Notion 등록과 Apps Script 속성 기록 사이에 원자적 트랜잭션은 없으므로 정확한 등록 이벤트 경계는 별도 등록기 연동 없이는 보장하지 않는다.

조회/조각/manifest 저장 실패는 자동 처리를 시작하지 않는다. 미완료 조각은 다음 초기 설정에서 재작성하지만, 확정된 manifest의 조각 누락/손상은 오류로 중단하고 스냅샷을 임의로 재작성하지 않는다. 값당 약4KB 미만, 5,000 ID 상한 및 기존 속성을 포함한 보수적400KB 추정 상한으로 저장 한도를 방어한다. 초과 시 자동 활성화하지 않는다. 실제 저장 API의 용량 오류도 동일하게 처리한다. 기준점 및 제외 ID 속성을 임의 변경/삭제하지 않는다.

전환 당시 미연결 83개를 포함한 기존 브랜드는 기준 스냅샷으로 제외하여 소급 생성하지 않는다. Drive URL이 비어 있고 브랜드명과 BO-숫자 4자리 이상 ID가 있는 새 브랜드만 처리한다. ID 발급 지연은 이후 실행에서 재확인하고 중복 ID는 오류로 중단한다. 기존 브랜드는 필요할 때 개별 폴더 버튼으로 처리한다.

## 회사·브랜드 표시 규격 및 재사용

새 폴더와 개별 처리한 기존 폴더의 바깥 이름은 `회사명 | 브랜드명 · 브랜드명 [BO-0001 · BO-0002]`다. 전체 BO ID를 숫자순으로 정렬하고 브랜드명을 같은 순서로 표시한다. 같은 Drive URL에 연결된 **모든 활성 브랜드**를 직접 조회하므로 공동 폴더의 기존 브랜드명을 빠뜨리지 않는다. 회사명은 회사 필드만 사용하며 벤더/공급사명으로 추측하지 않는다. 회사가 비어 있으면 `회사 미확인`, 기존 공동 폴더의 회사명이 서로 다르면 확인된 회사명들을 함께 표시한다. 회사/브랜드 원문의 하이픈은 유지한다.

확인된 표시명 예외: `BO-0065`의 회사 표시는 `에코프리베(주)`다. Notion의 복합 원문을 수정하지 않는다. 자사 `BO-0032`, `BO-0033`은 URL이 비어 있으면 개별 요청/자동 처리 모두 폴더를 만들지 않는다. 기존 기준 스냅샷을 유지하므로 과거 미연결 페이지의 소급 생성은 하지 않는다.

폴더 선택 순서는 다음과 같다.

1. 현재 Notion Drive URL
2. `BO_BRAND_FOLDER_PENDING_<page ID>` 또는 완료 후에도 남기는 `BO_BRAND_FOLDER_ID_<page ID>`
3. 자료 루트의 정확한 BO ID 구획 (`[BO-0001 · BO-0002]`, 기존 `[BO-0001] 이름`, `이름 (BO-0001)`)
4. 동일한 사업자번호(10자리 또는 3-2-5 하이픈 표기)를 가진 기존 브랜드의 **유일한** 폴더
5. 확인된 후보가 없으면 독립 신규 폴더

회사 이름 일치·유사성·빈 사업자번호만으로는 통합하지 않는다. 반복 숫자뿐인 자리 채움 값은 사업자번호로 사용하지 않는다. 사업자번호가 같아도 기존 폴더가 여러 개면 중단하고 관리자가 해당 신규 브랜드의 URL을 지정하도록 알린다. 기존 폴더끼리 합치거나 파일을 옮기지 않는다. 폴더에 적힌 BO ID 중 보관·조회 불가 또는 다른 URL 연결로 확인되지 않는 구성원이 있으면 이름을 줄이지 않고 중단한다. 기록된 URL/ID의 접근 불가·휴지통·권한 오류는 신규 생성으로 우회하지 않는다. 수동 이름 변경이나 회사명 변경 후에도 URL/영구 ID 기록으로 같은 폴더를 찾는다.

전역 잠금으로 버튼/트리거를 직렬화한다. 이름 변경·하위 폴더·양식 복사 전에 pending과 영구 ID를 저장하고, 준비 완료 후 URL이 빈 현재 브랜드에만 Drive URL을 기록한 다음 pending만 지운다. 실패 시 같은 폴더를 재사용한다. 기존 영업 단계 등 다른 Notion 속성은 변경하지 않는다.

하위 폴더는 `01_섬네일`, `02_상세페이지`, `03_서류`다. 기존 `01_상품 이미지`는 그대로 재사용하고 이름/내용/링크를 보존한다. 바깥 이름만 바꾸며 폴더 ID·부모·권한·기존 자식은 유지한다. 새 폴더는 상위 권한을 상속하고 공개 권한을 추가하지 않는다. 이미 URL이 있는 브랜드를 자동으로 일괄 처리하지 않으며 개별 처리 시 누락된 하위 폴더를 보완한다.

이 코드 변경은 입점 1분 polling, raw Form 기준점, 승인된 과거 두 응답 복구 로직을 변경하지 않는다. 배포만으로 과거 폴더 일괄 rename 작업을 다시 실행하지 않는다.


## 운영 배포 대상 보호

배포 workflow는 `scripts/verify-deploy-target.cjs`로 `PROD_SCRIPT_ID`와 확인된 실제 운영 프로젝트 ID의 동일 여부를 검사한다. `.clasp.json`/Google 인증 파일 생성 및 코드 업로드 전에 실행하며 불일치·미설정이면 중단한다. Secret 값은 출력하거나 변경하지 않고 성공 시 `운영 프로젝트 확인: 일치`만 기록한다. 대상은 `1npgGPeWwkUxCijrHFvDdG3RMTyUvz2kdv6tLoS1qDi4UntXgLSNfnVTS`이며, '(미사용)' 옛 단가표 프로젝트로 배포하지 않는다. 이 검사는 workflow 실행 시 적용되므로 코드 검토/모의 테스트만으로 현재 Secret의 실제 일치를 확인했다고 주장하지 않는다.

## 정확한 배포 순서 (이번 작업에서 실행하지 않음)

1. PR 코드/모의 테스트 검토. 테스트 Notion/Drive와 운영 설정의 분리를 확인한다.
2. Actions → **Apps Script 배포** → 작업 브랜치 → `target=test`, `mode=existing`, 설명 입력 → 실행. `TEST_SCRIPT_ID`, `TEST_DEPLOYMENT_ID`, `CLASPRC_JSON_BASE64`가 필요하다.
3. 테스트 프로젝트 소유자/관리자가 `setupBeautyora` 또는 설정 → 초기 설정 실행. 기준 manifest·제외 ID 조각·활성화 시각과 `scheduledBrandFolders` 1분 트리거를 확인한다. 초기 설정은 관리 대상 두 핸들러만 올바른 주기로 교체해 중복을 정리한다. 새 트리거 생성 성공 후 이전 트리거를 제거하며 다른 핸들러는 그대로 보존한다. 별도 등록 프로젝트에서 실행하지 않는다.
4. 테스트 DB에서 전환 전 브랜드 무변경, 같은 분의 기존/신규 구분, 스냅샷 실패 시 비활성 유지, 전환 후 신규 페이지의 ID 지연, ID 확정 후 폴더/URL, 재시도/기존 폴더 재사용을 검증한다. 운영 DB에는 테스트 브랜드를 만들지 않는다.
5. 승인 후 merge. Actions → **Apps Script 배포** → `main`, `target=production`, `mode=existing`, 설명 입력 → 실행. `PROD_SCRIPT_ID`, `PROD_DEPLOYMENT_ID`, 인증 Secret이 필요하다. 보고된 운영 버전106은 이 작업에서 변경하지 않았다.
6. 운영 소유자가 초기 설정을 한 번 실행해 전환 시각을 확정한다. 초기 스냅샷에 포함된 배포·설정 중 실제 신규 브랜드는 자동 대상에서 제외되므로 해당 건만 개별 처리한다. 시간 트리거는 프로젝트 최신 코드를 실행하므로 웹앱 버전 갱신과 별개다.
7. 연결 상태/트리거 실행 기록 및 다음 실제 신규 브랜드의 폴더·URL·공유 상속 상태를 확인한다. 기준 스냅샷과 기존 브랜드 속성 무변경을 확인한다. 실패는 로그 및 기존 관리자 알림으로 확인한다.
8. **실제 속성 삭제는 별도 등록기의 무의존성 확인 이후에만 한다.** 현재 등록기 소스가 없어 생성 payload가 `드라이브 폴더 만들기` 속성을 사용하는지 미확인이다. 운영센터 정상 동작만으로 삭제하면 등록기가 깨질 수 있다. 부모가 요청한 등록기 Apps Script 편집 링크/소스를 확보하여 페이지 생성·수정 payload와 스키마 참조를 확인하고, 필요한 수정 및 등록 검증까지 완료한 뒤 배포 확인과 함께 삭제를 조율한다. 이 PR은 운영센터 코드/UI 의존성만 제거한다.

## 중지·복구

중지 시 운영 프로젝트의 `scheduledBrandFolders` 트리거만 중지/제거한다. 기준 manifest·제외 ID 조각·활성화 시각, pending 속성, 폴더/URL을 보존한다. 재개 시 초기 설정은 기준점을 유지하고 미완료 신규 건을 따라잡는다. 웹앱 배포 버전만 롤백하면 시간 트리거 소스는 그대로다. 트리거를 중지한 뒤 승인된 소스도 복원해야 한다. 체크박스 삭제 이후 과거 버전의 트리거를 무심코 재개하지 않는다.
