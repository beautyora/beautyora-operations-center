# 신규 접수 브랜드 식별과 별칭 검토

## 조사 근거와 한계

2026-10-10 조사 기준 main은 `60d1afc002ee08ddd9114c6c1faff34b9b5b7f47`이다. 기존 `intakeProcessResponse_`는 응답 ID/journal 복구 후 정규화 브랜드명 완전 일치만 검사했다. `normalizeName_('DI/RE')`와 `normalizeName_('디르')`는 다르므로 이름이 다르면 신규 BO ID를 발급했다. 폴더는 별도로 사업자번호로 재사용하므로 **공유 폴더가 있어도 Notion 브랜드 중복은 막지 못한다**.

[운영 배포 실행](https://github.com/beautyora/beautyora-operations-center/actions/runs/37312387026)의 실제 로그를 읽어 2026-10-05 12:51 UTC, `e93e3a9f2ce3836b186334841917a15063dd8bf7`, 운영 대상 guard 일치, 웹앱 v115 성공을 재확인했다. 해당 커밋과 조사 main의 접수·정규화·폴더 코드는 동일하다. 이는 10월 9일 사건의 실행 로그 증명이 아니다. 시간 트리거는 프로젝트 최신 소스를 사용하므로 웹앱 버전만으로 당시 소스를 확정하지 않는다.

2026-10-10 데이터 담당자가 승인된 운영 프로젝트 설정에서 이 사건의 정확한 응답 journal만 읽어 값이 `{"done":true}`이고 다른 필드가 없음을 확인했다(담당자 전달 결과). BO-0137의 복원 가능한 휴지통 이동도 완료했으며 활성 브랜드에는 BO-0108만 남는다. 신규 신청 원문은 기존 페이지 본문에 보존됐고 기존 `폼 응답 ID` 속성은 공란이다. 담당자는 Script Properties/journal/코드를 변경하지 않았다. 이 코드 작업에서는 운영 데이터를 수정하지 않았다. 현행 코드의 완료 journal 선행 검사에 따라 해당 응답은 페이지 보관 이후에도 건너뛰며, 속성에 응답 ID를 추가할 필요가 없다. 실제 사건 당시 트리거 소스/실행 로그는 여전히 미확인이다.

배포 후 브라우저 담당자 실측: 실제 운영 프로젝트의 시간 기반 `scheduledBrandIntake` Head 트리거가 유지되고 2026-10-10 03:51:35 UTC(4.17초), 03:52:35 UTC(3.666초) 자동 실행이 완료됐다. `scheduledBrandFolders`도 03:52:24 UTC에 완료됐다. 수동 실행은 하지 않았다. 다른 사용자 소유의 기존 오류 `scheduledBeautyoraSync`와 비활성 옛 `handleBrandFormSubmit`은 변경하지 않았다. 이는 자동 실행 완료의 증거이며 새 신청 E2E 증거가 아니다.

라이브 소스도 브라우저 담당자가 실제 편집기에서 읽기 확인했다: `18_BrandIntake.gs` 405행 `notifyReviews === true`, 200행 BO-0108 별칭 집합, 369행 `intakeReviewNotice_` 및 시간당 재시도/실패 `waiting` 처리. 저장 버튼 비활성 상태였으며 소스를 저장하거나 변경하지 않았다.

런타임 원인 확정에 필요한 읽기 정보:

- 현재 핵심 소스는 위 라이브 확인을 마쳤다. 사건 당시 소스 확정에는 10월 5일~9일 코드 push/배포 이력과 마지막 수정 시각이 추가로 필요하다.
- 2026-10-09 13:30 UTC 전후 `scheduledBrandIntake` 실행 시각·핸들러·성공/오류·`intake.created` BO ID, 같은 시간대 다른 등록 핸들러 유무.
- 해당 응답 journal의 완료 상태는 위와 같이 확인됐다. 기준점/제외 조각은 미확인이지만 `{done:true}` 선행 검사로 재생성을 건너뛰는 판단에는 필요하지 않다. 추가 조사에서도 토큰·원문·연락처는 보고서나 로그에 복사하지 않는다.

이 변경은 [PR46](https://github.com/beautyora/beautyora-operations-center/pull/46)으로 병합됐으며 [운영 배포 실행](https://github.com/beautyora/beautyora-operations-center/actions/runs/38022008374)에서 2026-10-10 03:51:30 UTC에 v116 배포가 성공했다. 배포 커밋은 `a4d630ffdfd81d333c1c9e0d3f51bbdb8698ec8c`, 대상은 `production`, 방식은 `existing`이고 guard 일치를 확인했다. 승인 head `4753403`의 서버·Chromium CI 및 배포 중 서버 106개 테스트가 통과했다. 소스 19개 push는 03:51:27 UTC에 완료됐고 기존 실행/접근 매니페스트는 유지됐다. 이는 다음 실제 신규 접수의 운영 검증 완료를 뜻하지 않는다. 조사 중 Notion, Form, 응답 시트, Drive, 운영 Script Properties, 트리거는 변경하지 않았다.

## 판정 규칙

1. 기존 `done` journal, 원본 응답 토큰, 미완료 생성 page ID, 불명확 POST 차단을 먼저 적용한다. 기존 baseline/제외 응답/처리 기록은 초기화하거나 소급 변경하지 않는다.
2. 확인된 별칭 `DI/RE`, `디르`, `디르(DI/RE)`는 `BO-0108`에 연결한다. 대상 BO ID가 유일하고 활성 상태이며 이름도 확인된 집합에 있고, 신청/기존 사업자번호가 10자리 형식으로 일치해야 한다(같은 숫자 10회인 임시값 제외). 다른 페이지가 같은 별칭을 점유하거나 대상이 보관/이동/이름 변경되면 검토한다. 이 별칭 집합은 사용자 확인 사례에서 나온 것이며 일반 한영 자동 번역 규칙이 아니다.
3. 정확한 정규화 이름도 유일한 기존 브랜드와 사업자번호를 대조한다. 누락·불일치는 검토한다. 회사명/사업자번호/이메일만으로 기존 브랜드에 병합하지 않는다.
4. 괄호에 알려진 이름이 있지만 확인되지 않은 별칭이면 검토한다. 다른 이름인데 같은 사업자번호 또는 이메일이 있거나 신규 사업자번호가 누락/잘못된 형식이면 검토한다. 모호한 POST의 예약 journal도 신규 사업자/이메일 해시 충돌을 막는다. 이전 버전의 예약에는 이 해시가 없으므로 운영 적용 전 미완료 기록은 별도로 대조한다.
5. 검토 상태는 journal의 `phase: review`, 이유 코드, 이름 해시로 남는다. 반복 폴링은 검토를 재평가하지만 자동 생성/병합하지 않는다. 같은 사유의 오류 로그를 매분 반복하지 않으며 실행 결과의 `failed`에 계속 표시한다. 원문/개인 연락처는 오류에 넣지 않는다. 알림은 아래의 별도 전달 상태를 사용한다.
6. 기존 브랜드로 확정하면 `matched` 상태에 BO ID/page ID를 기록한다. 전체 완료 후에도 `done: true, matches` 연결을 남긴다. 부분 실패 재시도에서 이를 신규 생성 복구로 오인하지 않는다. 기존 영업값·신청 속성·폼 응답 ID·본문·Drive는 쓰지 않는다. 새 신청 원문은 원본 Form/응답 시트에 보존되며, 기존 Notion에 새 신청 내용을 옮기는 작업은 별도 승인된 데이터 정리 절차다.
7. 승인된 별개 브랜드는 신규 BO ID/신청 내용을 새 페이지에 기록한다. 기존 폴더 재사용 규칙과 불명확 POST/Drive 재시도 보호를 유지한다. 같은 응답의 복수 브랜드도 각각 판정한다. 앞서 생성한 브랜드와 사업자/이메일이 같으면 나머지도 검토하며, 별개 브랜드로 확인한 각 이름에 응답 한정 승인을 사용한다. 확인된 별칭은 기존 ID로 연결한다.

## 검토 알림의 전달 상태

- 검토 판정 저장을 알림 전달로 간주하지 않는다. `entry.notice.sentAt`은 `MailApp.sendEmail` 성공(또는 동일 응답·항목·사유의 성공 캐시)이 확인된 뒤에만 기록한다. 메일 서비스의 발송 수락이며 최종 수신함 도착 확인은 아니다.
- 알림 키는 응답 journal 키 + 항목 index + 검토 사유다. 서로 다른 신청 A/B는 같은 제목이어도 각각 알리고, 일반 운영 오류의 제목별 12시간 cooldown은 검토 알림을 막지 않는다. 발송된 검토는 journal의 `sentAt`으로 캐시 만료 후에도 반복 발송하지 않는다.
- 관리자 미설정, 수신자 수보다 적은 잔여 쿼터, 일시적인 발송 실패는 미전달 상태로 유지한다. 발송 시도 전에 `nextAttemptAt`을 저장하여 실패/실행 중단 뒤에도 **시간당 최대 한 번** 재시도한다. 검토가 해소되면 이전 알림은 발송하지 않는다. 별도 최대 횟수로 포기하지 않으므로 다음 날 쿼터 회복 후에도 재개할 수 있다.
- 수동 sync는 검토 결과를 보여 주며 알림을 소비하지 않는다. API payload 객체는 발송 플래그로 해석하지 않고 내부 호출의 boolean `true`만 발송을 허용한다. 다음 정기 트리거가 보낸다. 반환값 `notification`은 `pending`(정기 발송 대기), `waiting`(재시도 대기), `sent`(발송 수락 확인)다. 검토 항목의 `notify: false`는 제목별 묶음 알림에서 제외한다는 뜻이다.
- 메일 발송과 Script Properties 저장은 원자적 트랜잭션이 아니다. 발송 후 journal 확정 실패는 성공 캐시로 재발송을 막고 다음 재시도에서 확정한다. 확정 저장 실패와 캐시 유실이 겹치면 중복 메일 가능성이 있으며, 이때도 시도 간격은 최소 1시간이다. 정확히 한 번의 외부 메일 전달을 보장한다고 주장하지 않는다.

## 검토 후 설정 (별도 승인 필요)

`BO_INTAKE_MATCH_RULES_V1` Script Property의 JSON으로 추가 별칭 또는 특정 신규 생성 판단을 표현한다. 이 PR은 운영 속성을 설정하지 않는다. 관리자 화면/API를 새로 공개하지 않는다.

```json
{
  "aliases": [{ "code": "BO-0123", "names": ["확인된 정식 이름", "확인된 별칭"] }],
  "newBrands": [{ "responseHash": "64자리 SHA-256", "fingerprint": "64자리 SHA-256", "nameHash": "64자리 SHA-256" }]
}
```

- 별칭은 업무 담당자가 동일 브랜드임을 확인한 경우만 등록한다. 기존 코드의 확인된 별칭과 충돌하는 매핑은 검토로 중단한다. 사업자번호가 같다는 이유만으로 별칭을 등록하지 않는다.
- `newBrands`는 같은 회사의 별개 브랜드 등 **신규 생성이 확인된 특정 응답**에만 사용한다. `responseHash`는 원본 FormResponse ID 해시(기존 journal 키 접미사), `fingerprint`는 해당 journal의 값, `nameHash`는 검토 entry의 값이다. 응답 원문을 속성/로그에 복사하지 않는다. 세 값 모두 일치해야 하며 다른 응답/수정된 응답/다른 브랜드명에 승인이 전이되지 않는다.
- 신규 승인도 기존 이름/확인 별칭 충돌, 불명확 POST, 변경된 응답 차단은 우회하지 않는다. 기존 alias 대상의 사업자 정보가 누락되면 업무 데이터 확인/별도 정리가 먼저다.
- 설정 저장 후 기존 폴링이 미완료 검토 건을 재평가한다. `setupBrandIntake` 재실행, journal/baseline 삭제, 과거 전체 replay는 필요하지 않으며 실행하지 않는다. 처리 중 응답이 수정됐으면 자동 재처리하지 않고 별도 검토한다.

## 이미 보관했거나 정리 중인 중복 페이지

현행 코드의 `{done:true}` journal은 Notion 조회보다 먼저 응답을 건너뛴다. 따라서 중복 페이지를 휴지통으로 옮겨도 이 기록이 유지되면 재생성하지 않는다. 미완료 journal에 생성 page ID가 남아 있고 해당 페이지가 안 보이면 재생성을 중단한다. `creating`이 남았지만 페이지가 안 보이는 경우도 중단한다. baseline은 최초 활성화 당시 응답의 제외 목록이며, 이후 모든 완료 응답이 자동 추가되는 목록이 아니다.

journal이 유실되고 baseline 제외에도 없는 응답은 재처리될 수 있으므로 정리 전에 실제 기록을 읽어 확인한다. 기록을 지우지 않는다. 이 변경의 별칭 보호는 v116 코드 push 이후 적용 대상이며, 해당 과거 완료 응답을 소급 재처리하지 않는다.

기존 페이지의 빈 `폼 응답 ID`를 중복 응답 ID로 채우는 것은 단순 중복 표시가 아니다. 현행 미완료 경로는 그 페이지를 응답이 생성한 페이지로 간주하여 **폴더 복구를 호출**한다. 두 활성 페이지에 같은 토큰이 있으면 오류가 난다. 재생성 방지를 위해 해당 속성을 임의 연결하지 말고 journal을 먼저 확인한다.

## 검증 및 적용 계획

Node.js 22 전체 서버 테스트 106개 통과, 설치된 시스템 Chromium으로 UI E2E 통과, 정적 운영센터 빌드와 `git diff --check` 통과. 로컬 Playwright 지정 Chromium 다운로드는 환경의 도메인 제한(HTTP 403)으로 차단되어 시스템 Chromium을 사용했다. PR CI에서는 지정 버전을 확인한다.

가짜 Form/Notion/Drive로 확인된 별칭, 같은 회사 별개 브랜드 검토/승인/공유 폴더, 충돌·누락·괄호 별칭, 부분 실패 재시도, 보관된 완료/미완료 응답, 기존 단계·원문·baseline 보존을 검증한다. 모의 검증은 실제 운영 E2E가 아니다.

사용자의 2026-10-10 병합·배포 승인에 따라 위 v116까지 반영했다. setup/replay 없이 기존 baseline/journal을 유지했다. 시간 트리거는 소스 push부터 영향을 받는다. 배포 후 자동 트리거 실행은 위 담당자 실측으로 확인됐다. 현재 핵심 소스도 편집기에서 확인했다. 로그인된 운영 화면 상태와 다음 정상 접수의 생성/검토 결과·기존 영업값·응답 보존·폴더 연결·재시도 중복 여부는 별도 확인 대상이다. 실제 신규 테스트 제출은 승인받지 않았으며 실행하지 않았다.
