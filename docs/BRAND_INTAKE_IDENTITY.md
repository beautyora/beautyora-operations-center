# 신규 접수 브랜드 식별과 별칭 검토

## 조사 근거와 한계

2026-10-10 조사 기준 main은 `60d1afc002ee08ddd9114c6c1faff34b9b5b7f47`이다. 기존 `intakeProcessResponse_`는 응답 ID/journal 복구 후 정규화 브랜드명 완전 일치만 검사했다. `normalizeName_('DI/RE')`와 `normalizeName_('디르')`는 다르므로 이름이 다르면 신규 BO ID를 발급했다. 폴더는 별도로 사업자번호로 재사용하므로 **공유 폴더가 있어도 Notion 브랜드 중복은 막지 못한다**.

[운영 배포 실행](https://github.com/beautyora/beautyora-operations-center/actions/runs/37312387026)의 실제 로그를 읽어 2026-10-05 12:51 UTC, `e93e3a9f2ce3836b186334841917a15063dd8bf7`, 운영 대상 guard 일치, 웹앱 v115 성공을 재확인했다. 해당 커밋과 조사 main의 접수·정규화·폴더 코드는 동일하다. 이는 10월 9일 사건의 실행 로그 증명이 아니다. 시간 트리거는 프로젝트 최신 소스를 사용하므로 웹앱 버전만으로 당시 소스를 확정하지 않는다.

런타임 원인 확정에 필요한 읽기 정보:

- 승인된 운영 프로젝트의 현재 `18_BrandIntake` 소스와 마지막 수정 시각, 10월 5일 이후 코드 push/배포 이력.
- 2026-10-09 13:30 UTC 전후 `scheduledBrandIntake` 실행 시각·핸들러·성공/오류·`intake.created` BO ID, 같은 시간대 다른 등록 핸들러 유무.
- 해당 원본 응답 ID의 SHA-256에 해당하는 `BO_INTAKE_JOB_V1_<hash>` 값과 `BO_INTAKE_BASELINE_V1` 및 제외 조각의 포함 여부. 토큰·원문·연락처는 보고서나 로그에 복사하지 않는다.

이 변경은 미배포 코드이며 운영 문제 해결 완료를 뜻하지 않는다. 조사 중 Notion, Form, 응답 시트, Drive, 운영 Script Properties, 트리거는 변경하지 않았다.

## 판정 규칙

1. 기존 `done` journal, 원본 응답 토큰, 미완료 생성 page ID, 불명확 POST 차단을 먼저 적용한다. 기존 baseline/제외 응답/처리 기록은 초기화하거나 소급 변경하지 않는다.
2. 확인된 별칭 `DI/RE`, `디르`, `디르(DI/RE)`는 `BO-0108`에 연결한다. 대상 BO ID가 유일하고 활성 상태이며 이름도 확인된 집합에 있고, 신청/기존 사업자번호가 10자리 형식으로 일치해야 한다(같은 숫자 10회인 임시값 제외). 다른 페이지가 같은 별칭을 점유하거나 대상이 보관/이동/이름 변경되면 검토한다. 이 별칭 집합은 사용자 확인 사례에서 나온 것이며 일반 한영 자동 번역 규칙이 아니다.
3. 정확한 정규화 이름도 유일한 기존 브랜드와 사업자번호를 대조한다. 누락·불일치는 검토한다. 회사명/사업자번호/이메일만으로 기존 브랜드에 병합하지 않는다.
4. 괄호에 알려진 이름이 있지만 확인되지 않은 별칭이면 검토한다. 다른 이름인데 같은 사업자번호 또는 이메일이 있거나 신규 사업자번호가 누락/잘못된 형식이면 검토한다. 모호한 POST의 예약 journal도 신규 사업자/이메일 해시 충돌을 막는다. 이전 버전의 예약에는 이 해시가 없으므로 운영 적용 전 미완료 기록은 별도로 대조한다.
5. 검토 상태는 journal의 `phase: review`, 이유 코드, 이름 해시로 남고 기존 관리자 오류 알림 경로로 전달된다. 반복 폴링은 검토를 재평가하지만 자동 생성/병합하지 않는다. 원문/개인 연락처는 오류에 넣지 않는다.
6. 기존 브랜드로 확정하면 `matched` 상태에 BO ID/page ID를 기록한다. 전체 완료 후에도 `done: true, matches` 연결을 남긴다. 부분 실패 재시도에서 이를 신규 생성 복구로 오인하지 않는다. 기존 영업값·신청 속성·폼 응답 ID·본문·Drive는 쓰지 않는다. 새 신청 원문은 원본 Form/응답 시트에 보존되며, 기존 Notion에 새 신청 내용을 옮기는 작업은 별도 승인된 데이터 정리 절차다.
7. 승인된 별개 브랜드는 신규 BO ID/신청 내용을 새 페이지에 기록한다. 기존 폴더 재사용 규칙과 불명확 POST/Drive 재시도 보호를 유지한다. 같은 응답의 복수 브랜드도 각각 판정한다. 앞서 생성한 브랜드와 사업자/이메일이 같으면 나머지도 검토하며, 별개 브랜드로 확인한 각 이름에 응답 한정 승인을 사용한다. 확인된 별칭은 기존 ID로 연결한다.

## 검토 후 설정 (별도 승인 필요)

`BO_INTAKE_MATCH_RULES_V1` Script Property의 JSON으로 추가 별칭 또는 특정 신규 생성 판단을 표현한다. 이 PR은 운영 속성을 설정하지 않는다. 관리자 화면/API를 새로 공개하지 않는다.

```json
{
  "aliases": [{ "code": "BO-0123", "names": ["확인된 정식 이름", "확인된 별칭"] }],
  "newBrands": [{ "responseHash": "64자리 SHA-256", "fingerprint": "64자리 SHA-256", "nameHash": "64자리 SHA-256" }]
}
```

- 별칭은 업무 담당자가 동일 브랜드임을 확인한 경우만 등록한다. 기존 코드의 확인된 별칭과 충돌하는 매핑은 검토로 중단한다. 사업자번호가 같다는 이유만으로 별칭을 등록하지 않는다.
- `newBrands`는 같은 회사의 별개 브랜드 등 **신규 생성이 확인된 특정 응답**에만 사용한다. `responseHash`는 원본 FormResponse ID 해시(기존 journal 키 접미사), `fingerprint`는 해당 journal의 값, `nameHash`는 검토 entry의 값이다. 응답 원문을 속성/로그에 복사하지 않는다. 세 값 모두 일치해야 하며 다른 응답/수정된 응답/다른 브랜드명에 승인이 전이되지 않는다.
- 신규 승인도 기존 이름/확인 별칭 충돌, 불명확 POST, 변경된 응답 차단은 우회하지 않는다. 기존 alias 대상의 사업자 정보가 누락되면 업무 데이터 확인/별도 정리가 먼저다.
- 설정 저장 후 기존 폴링이 미완료 검토 건을 재평가한다. `setupBrandIntake` 재실행, journal/baseline 삭제, 과거 전체 replay는 필요하지 않으며 실행하지 않는다. 처리 중 응답이 수정됐으면 자동 재처리하지 않고 별도 검토한다.

## 이미 보관했거나 정리 중인 중복 페이지

현행 코드의 `{done:true}` journal은 Notion 조회보다 먼저 응답을 건너뛴다. 따라서 중복 페이지를 휴지통으로 옮겨도 이 기록이 유지되면 재생성하지 않는다. 미완료 journal에 생성 page ID가 남아 있고 해당 페이지가 안 보이면 재생성을 중단한다. `creating`이 남았지만 페이지가 안 보이는 경우도 중단한다. baseline은 최초 활성화 당시 응답의 제외 목록이며, 이후 모든 완료 응답이 자동 추가되는 목록이 아니다.

journal이 유실되고 baseline 제외에도 없는 응답은 재처리될 수 있으므로 정리 전에 실제 기록을 읽어 확인한다. 기록을 지우지 않는다. 이 변경의 별칭 보호는 배포 전에는 적용되지 않는다.

기존 페이지의 빈 `폼 응답 ID`를 중복 응답 ID로 채우는 것은 단순 중복 표시가 아니다. 현행 미완료 경로는 그 페이지를 응답이 생성한 페이지로 간주하여 **폴더 복구를 호출**한다. 두 활성 페이지에 같은 토큰이 있으면 오류가 난다. 재생성 방지를 위해 해당 속성을 임의 연결하지 말고 journal을 먼저 확인한다.

## 검증 및 적용 계획

Node.js 22 전체 서버 테스트 98개 통과, 설치된 시스템 Chromium으로 UI E2E 통과, 정적 운영센터 빌드와 `git diff --check` 통과. 로컬 Playwright 지정 Chromium 다운로드는 환경의 도메인 제한(HTTP 403)으로 차단되어 시스템 Chromium을 사용했다. PR CI에서는 지정 버전을 확인한다.

가짜 Form/Notion/Drive로 확인된 별칭, 같은 회사 별개 브랜드 검토/승인/공유 폴더, 충돌·누락·괄호 별칭, 부분 실패 재시도, 보관된 완료/미완료 응답, 기존 단계·원문·baseline 보존을 검증한다. 모의 검증은 실제 운영 E2E가 아니다.

리뷰·병합·운영 배포는 별도 승인 후 수행한다. 배포 전 실제 소스/트리거/미완료 journal과 데이터 담당자의 중복 정리 완료 상태를 읽기 대조한다. 승인된 target guard 절차로 코드를 반영하되 setup/replay 없이 기존 baseline/journal을 유지한다. 시간 트리거는 소스 push부터 영향을 받는다. 배포 후 다음 정상 접수를 관찰하여 생성/검토 결과·기존 영업값·응답 보존·폴더 연결·재시도 중복 여부를 확인한다. 실제 신규 테스트 제출은 별도 승인 범위다.
